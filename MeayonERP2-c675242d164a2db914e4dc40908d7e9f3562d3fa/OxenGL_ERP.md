# البرومبت الاحترافي لتدقيق وإصلاح مشروع OxenGL / Meayon ERP

انسخ النص التالي بالكامل إلى أداة الذكاء الاصطناعي التي ستستخدمها لبرمجة المشروع. أرفق معه ملف المشروع المضغوط أو امنحه الوصول إلى مستودع المشروع.

---

## نص البرومبت

أنت مهندس برمجيات أول، ومهندس حلول SaaS، وخبير أمن تطبيقات، ومراجع جاهزية إنتاج، ومتخصص في أنظمة ERP والخدمات اللوجستية في السوق السعودي. مطلوب منك تنفيذ **تدقيق حقيقي شامل** لمشروع `OxenGL / Meayon ERP` المرفق، ثم إعداد خطة إصلاح تنفيذية، ثم تنفيذ الإصلاحات على مراحل بعد توثيقها.

لا تعتمد على أسماء الملفات أو الانطباع البصري أو الوصف الموجود في README. يجب أن تقرأ الكود الفعلي، وتطابق الوحدات، وتشغّل الفحوصات، وتثبت كل نتيجة بمسار الملف ورقم السطر أو بنتيجة أمر قابل لإعادة التنفيذ. لا تخمّن. إذا لم تستطع التحقق من شيء، اكتب صراحة: **غير متحقق منه**، واذكر ما يلزم للتحقق.

لا تعتبر نجاح Build دليلًا على جاهزية الإنتاج. يجب الفصل بين:

1. ما تم التحقق منه فعليًا.
2. ما هو موجود لكنه ناقص.
3. ما هو موجود شكليًا أو تجريبيًا.
4. ما هو غير موجود.
5. ما فشل تشغيله أو اختباره.
6. ما يحتاج مراجعة قانونية أو اعتمادًا رسميًا.

# المرحلة الأولى: قواعد السلامة قبل الفحص

1. لا تشغّل أو ترفع أو ترسل أي مفتاح سري أو كلمة مرور أو شهادة أو ملف `.env` حقيقي.
2. لا تنشر المشروع ولا تتصل ببيئة إنتاج ولا تغير بيانات حقيقية.
3. لا تستخدم حسابات أو كلمات مرور موجودة في المشروع إلا في بيئة محلية معزولة وبعد توضيح الغرض.
4. إذا وجدت مفاتيح SSH أو مفاتيح API أو كلمات مرور داخل المشروع، لا تطبع محتواها. اذكر مسار الملف ونوع السر وحجمه وبصمته المنقحة فقط، ثم صنّفها كخطر.
5. لا تحذف ملفات أو تعدل الكود قبل إنشاء تقرير الحالة الأولية ونسخة Git أو نقطة استعادة.
6. أي إصلاح تدميري أو تغيير مخطط قاعدة بيانات يجب أن يكون له Migration وخطة Rollback.
7. لا تعتبر وجود شعار أو QR أو عبارة “متوافق مع ZATCA” دليلًا على الاعتماد أو الامتثال.

ابدأ بجرد كامل للمشروع، ويتضمن ذلك:

- جميع المجلدات والملفات.
- Backend وFrontend وأي تطبيق جوال.
- أطر العمل واللغات والإصدارات.
- ملفات الاعتماديات.
- ملفات البيئة والإعدادات.
- Docker وCompose وNginx وCI/CD.
- migrations وseed وfixtures.
- الاختبارات.
- الأرشيفات المتداخلة ونسخ المصدر المتعددة.
- ملفات المفاتيح والشهادات والأسرار.
- الملفات غير المستخدمة أو المكررة.
- الملفات التي لا ينبغي أن تكون في المستودع مثل `node_modules`, `dist`, قواعد البيانات المحلية، وملفات الأسرار.

أنشئ جدولًا باسم **Project Inventory** يحتوي على المسار، النوع، الوظيفة، الحالة، وهل هو مصدر حقيقة أم نسخة قديمة.

حدد بوضوح نسخة المصدر المعتمدة. إذا وجدت أكثر من Frontend أو Backend أو أرشيف مصدر، لا تفترض أيها الصحيح؛ قارنها وأصدر حكمًا موثقًا.

## متطلب إلزامي لتحديد قواعد البيانات ومصادر التخزين

قبل الانتقال إلى المراحل التالية، حدد صراحة كل مخزن بيانات يستخدمه المشروع، بما في ذلك قواعد SQL وNoSQL، وملفات SQLite، واتصالات PostgreSQL أو MySQL، وFirebase Authentication، وFirestore، وتخزين الملفات، و`localStorage`، و`sessionStorage`، وIndexedDB، وبيانات Mock، وبيانات Seed، وملفات JSON، وCache، وQueues، وأي خدمة بيانات خارجية.

أنشئ جدولًا باسم **Database and Storage Inventory** بالأعمدة التالية:

| مخزن البيانات | التقنية | مسار الملف أو الإعداد | المستخدم من | البيانات المخزنة | البيئة | مصدر الحقيقة؟ | عزل المستأجر؟ | الدليل |
|---|---|---|---|---|---|---|---|---|

ثم قدم نتيجة مباشرة لا تحتمل اللبس تجيب عن الأسئلة التالية:

1. ما قاعدة البيانات التي يستخدمها Backend افتراضيًا فعلًا؟
2. ما قاعدة البيانات التي يستخدمها Docker أو إعداد الإنتاج فعلًا؟
3. هل يستخدم Frontend قاعدة بيانات أو نظام تخزين مختلفًا؟
4. هل يتم تخزين البيانات في `localStorage` أو Firebase/Firestore أو ملفات Mock أو أي مصدر محلي آخر؟
5. ما مصدر الحقيقة لكل كيان تجاري؟
6. هل توجد مصادر حقيقة متعددة متنافسة؟
7. هل يمكن أن تفقد البيانات أو تختلف أو تصبح قديمة أو تظهر في متصفح واحد فقط؟
8. ما معمارية قاعدة البيانات المطلوبة لـ SaaS في الإنتاج، وما خطوات الترحيل إليها؟

لا تكتب “المشروع يستخدم قاعدة البيانات X” إلا بعد التحقق من Connection String، وكود التهيئة، وإعداد Docker، والـ migrations، ومسارات القراءة والكتابة الفعلية. إذا كانت البيئات المختلفة تستخدم قواعد بيانات مختلفة، فاذكر كل بيئة على حدة واشرح النتائج المترتبة.

# المرحلة الرابعة: تحليل Backend

افحص Backend بالتفصيل، بما في ذلك:

## المعمارية

- إطار العمل والتنظيم.
- هل هو Modular Monolith أو Microservices أو خليط غير منظم.
- حدود الوحدات.
- وجود فصل بين Router وService وRepository وSchema.
- الملفات الكبيرة جدًا والمسؤوليات المتعددة.
- التكرار والاقتران الزائد.
- إدارة الإعدادات والبيئة.
- قابلية الاختبار والتوسع.

## المصادقة

تحقق من:

- تسجيل الدخول والتسجيل وتفعيل الحساب.
- JWT أو Sessions أو OAuth أو Firebase.
- مدة التوكن.
- Refresh Token.
- إبطال الجلسات.
- MFA.
- إعادة تعيين كلمة المرور.
- Rate Limiting.
- قفل الحساب.
- الحسابات الافتراضية.
- الأسرار الافتراضية.
- هل يوجد مسار غير محمي ينشئ مستخدمين أو يمنح Admin.
- هل تتحقق المنظومة من Firebase ID Token فعلًا أم تكتفي بالبيانات التي يرسلها المتصفح.

## الصلاحيات

اختبر الصلاحيات على مستوى API لا الواجهة فقط. تحقق من:

- RBAC.
- صلاحيات الوحدة والعملية والسجل.
- نطاق الفرع والمشروع.
- تصعيد الصلاحيات.
- IDOR.
- الوصول إلى سجلات مستخدم أو مستأجر آخر.
- صلاحيات مدير المنصة مقابل مدير العميل.
- صلاحيات الدعم المؤقتة.
- أثر تغيير الدور أو تعطيل المستخدم.

## Multi-Tenant

حدد هل النظام Multi-Tenant حقيقي أم مجرد ترخيص شكلي. افحص:

- وجود `tenant_id` في كل جدول أعمال.
- العضوية بين المستخدم والمستأجر.
- طريقة استخراج tenant من جلسة المستخدم.
- هل يقبل الخادم `tenant_id` من العميل ويثق به.
- الفهارس والقيود المركبة.
- الاستعلامات التي تستخدم `.all()` دون tenant filter.
- التخزين والملفات والتقارير والتصدير.
- السجلات العامة والـ Audit Log.
- عزل cache وjobs وnotifications.
- عزل مفاتيح التكامل لكل عميل.
- اختبارات محاولة قراءة أو تعديل بيانات مستأجر آخر.

نفّذ اختبارات سلبية صريحة على مستأجرين A وB، ولا تقبل أي نتيجة مبنية على قراءة الكود فقط.

## قاعدة البيانات

افحص:

- الجداول والعلاقات والمفاتيح الخارجية.
- القيود والفهارس.
- migrations وRollback.
- أنواع البيانات.
- استعمال Float في الأموال أو الأوزان.
- الترقيم والتزامن.
- Soft Delete.
- Audit fields.
- التواريخ والمناطق الزمنية.
- العملة والضريبة.
- مشاكل N+1.
- الاستعلامات غير المحددة النطاق.
- قابلية PostgreSQL والإنتاج.

## منطق الأعمال

راجع دورة العمل الفعلية:

```text
عميل/مورد → عقد → أمر توريد → رحلة → إسناد مركبة وسائق → تحميل → وزن → تسليم → تذكرة وزن → مراجعة → فاتورة → دفع → تقرير
```

تحقق من الحالات والانتقالات، ومنع الانتقالات غير المنطقية، وذرية العمليات، والتكرار عند إعادة الطلب، وتسجيل التعديلات، ودقة حساب الكمية والفاقد والضريبة والربح.

## API

أنشئ قائمة كاملة بكل المسارات، مع:

- Method.
- Path.
- Authentication.
- Required role.
- Tenant scope.
- Request schema.
- Response schema.
- Error responses.
- Frontend caller.
- حالة التنفيذ.

افحص اختلاف `snake_case` و`camelCase`، اختلاف أسماء الحقول، حالات HTTP، Pagination، Filtering، Sorting، Rate Limits، وIdempotency.

# المرحلة السابعة: التدقيق الأمني

نفّذ مراجعة OWASP عملية، بما فيها:

- Broken Access Control.
- IDOR.
- Authentication failures.
- Injection.
- XSS.
- CSRF.
- CORS.
- SSRF.
- رفع الملفات.
- Path Traversal.
- تسريب الأسرار.
- Rate Limiting.
- Session fixation.
- JWT algorithm/key issues.
- Security headers.
- CSP.
- Dependency vulnerabilities.
- Logs تحتوي بيانات حساسة.
- نسخ احتياطية غير محمية.
- مفاتيح Firebase أو cloud storage.
- مفاتيح SSH أو API داخل المستودع.

لكل ثغرة اذكر:

- رقمًا فريدًا.
- التصنيف.
- الشدة: Critical/High/Medium/Low.
- المسار ورقم السطر.
- خطوات إعادة الإنتاج في بيئة محلية فقط.
- الأثر.
- الإصلاح.
- اختبار منع التكرار.

# المرحلة العاشرة: خطة الإصلاح التنفيذية

```text

```

- ID.
- الأولوية P0/P1/P2/P3.

- الجداول أو migrations.
- API المتأثر.
- الواجهة المتأثرة.
- المخاطر.
- الاعتماديات.
- طريقة الاختبار.
- معيار القبول.

استخدم المراحل التالية ما لم يثبت التدقيق أن ترتيبًا آخر أفضل:

- إزالة الأسرار والمفاتيح من المشروع وتدويرها.
- إغلاق قواعد Firestore المفتوحة.

- تغيير الحسابات الافتراضية.
- منع الأسرار الافتراضية في الإنتاج.
- فصل بيانات الاختبار.

## P1: إعادة تأسيس الهوية وMulti-Tenant

- اختيار مصدر حقيقة واحد.
- توحيد المصادقة.
- إنشاء tenants وmemberships وroles وpermissions.
- إضافة tenant_id لكل جدول أعمال.
- إضافة قيود وفهارس مركبة.
- تطبيق TenantContext في كل طلب.

## P2: توحيد نموذج التشغيل

- العملاء والموردون والناقلون والمركبات والسائقون.
- العقود وأوامر التوريد.
- الرحلات وحالاتها.
- تذاكر الوزن وحساب الفاقد.
- التسليم والمرفقات.
- الفواتير والمدفوعات.
- التقارير.

## P3: الاستعداد التجاري السعودي

- ZATCA Adapter وتدفق الاختبار.
- Decimal والريال السعودي والضريبة.
- PDPL وPrivacy وRetention.
- الوثائق والتنبيهات.
- التصدير والاستعادة.

# المرحلة الحادية عشرة: التنفيذ الفعلي للإصلاحات

بعد تسليم التقريرين، لا تبدأ بإعادة كتابة كل المشروع. نفذ الإصلاحات على دفعات صغيرة. لكل دفعة:

1. أنشئ Branch أو نقطة استعادة.
2. اشرح نطاق الدفعة.
3. عدل أقل عدد ممكن من الملفات.
4. أنشئ migrations.
5. حدّث API.
6. حدّث Frontend.
7. أضف اختبارات.
8. شغّل الفحوصات.
9. افحص Regression.
10. قدم تقريرًا بالنتيجة.

لا تنتقل من P0 إلى P1 قبل إغلاق المخاطر الحرجة. لا تضف ميزة جديدة بينما يوجد تسرب بيانات أو مسار Admin غير محمي.

# معايير الإطلاق للإنتاج والبيع

لا تعلن أن المشروع جاهز للإنتاج إلا إذا تحققت جميع النقاط التالية:

- كل الأسرار خارج Git وتم تدوير المكشوف منها.
- لا توجد قواعد قاعدة بيانات عامة.
- لا يوجد مسار غير محمي يمنح صلاحية.
- كل جداول الأعمال معزولة بمستأجر.
- اختبارات العزل ناجحة.
- اختبارات الصلاحيات ناجحة.
- Frontend وBackend يستخدمان مصدر بيانات واحدًا.
- دورة الرحلة كاملة تعمل فعليًا.
- الفواتير والمبالغ تستخدم Decimal.
- توجد migrations ونسخ احتياطي واختبار استعادة.
- توجد مراقبة وتنبيهات وسجل أخطاء.
- لا توجد حسابات افتراضية معروفة.
- تعمل العربية وRTL والجوال.
- لا توجد ثغرات Critical أو High مفتوحة.
- اختبارات Backend وFrontend قابلة للتشغيل من أمر موحد.
- تم توثيق API وقاعدة البيانات والصلاحيات.
- تم توثيق سياسة البيانات والاحتفاظ والتصدير.
- تكامل ZATCA، إن كان ضمن نطاق الإطلاق، اجتاز اختبارات البيئة المناسبة ولم يتم وصفه بأنه معتمد دون دليل.
- تمت مراجعة المتطلبات النظامية السعودية مع مختص مؤهل.
- تم اختبار الأداء تحت حمل متوقع.
- توجد خطة Rollback وحوادث واستعادة.

# صيغة الرد الإلزامية في كل مرحلة

بعد كل مرحلة، أجب بالعناوين التالية:

```text
1. ما تم فحصه
2. ما تم التحقق منه فعليًا
3. ما لم يمكن التحقق منه
4. الأخطاء والمخاطر الجديدة
5. الملفات المتأثرة
6. نتائج الأوامر والاختبارات
7. القرارات والافتراضات
8. الأسئلة المفتوحة
9. معيار قبول المرحلة
10. الخطوة التالية
```

ممنوع استخدام عبارات مثل “تم إصلاح كل شيء” أو “جاهز للإنتاج” دون جدول تحقق يثبت كل معيار قبول.

ابدأ الآن بالمرحلة الأولى فقط: جرد المشروع وتحليل مصدر الحقيقة، ثم قدم تقريرًا أوليًا قبل تعديل أي كود.
