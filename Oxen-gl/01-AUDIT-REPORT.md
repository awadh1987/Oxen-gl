## 1. الملخص التنفيذي (Executive Summary)

أجرى فريق التدقيق فحصاً تقنياً شاملاً وميدانياً للمنظومة الرقمية `OxenGL / Meayon ERP` المتواجدة في الخادم والمستودع البرمجي. لم يعتمد الفحص على أي وعود تسويقية أو نصوص وصفية، بل استند حصراً إلى الكود المصدري الفعلي، وسجلات قواعد البيانات الحية، وفحوصات الأمان، ونتائج اختبارات التجميع والتشغيل.

### خلاصة النتائج الرئيسية:
1. **ازدواجية المعمارية وتعدد مصادر الحقيقة (Dual Architecture & Split Brain):**
   - المشروع يعاني من وجود نظامين منفصلين يعملان بالتوازي:
     - **النظام الأول (FastAPI Backend - Port 8000):** يمتلك قاعدة بيانات PostgreSQL متقدمة جداً (68 جدولاً)، محرك قيود محاسبية مزدوجة (Double-entry GAAP/IFRS)، نموذج Multi-Tenant عبر `company_id` و`TenantConnectionManager`، ومحول ZATCA Phase 2 تجريبي.
     - **النظام الثاني (React/Vite Frontend & Express Server - Port 3000):** يعمل بواجهة حديثة وغنية لكنه يعتمد بنسبة تتجاوز 85% على التخزين المحلي للمتصفح (`localStorage`) وبيانات وهمية (`INITIAL_*` في `mockData.ts`)، بينما خادم Express (`server.ts`) لا يرتبط إطلاقاً بقاعدة بيانات PostgreSQL ويقتصر على استدعاء Gemini AI وبعض المسارات الشكلية.
   - **النتيجة:** أي تعديل يجريه المستخدم في واجهة المتصفح (إضافة عميل، كسارة، ناقل، سند صرف، أو فاتورة) يُحفظ فقط في ذاكرة متصفحه المحلي ولا يصل إلى خادم المحاسبة المركزي في PostgreSQL، مما يؤدي لفقدان البيانات بمجرد مسح الـ Cache أو تبديل الجهاز.

2. **ثغرات أمنية حرجة غير مقبولة في الإنتاج (Critical Security Vulnerabilities):**
   - وجود ملف `SUPERADMIN_CREDENTIALS_AND_FINDINGS.md` في المستودع يحوي كلمات مرور مكشوفة وحسابات Super Admin ورمز الاستعادة السري بالكامل (`OXENGL_RECOVERY_CODE`).
   - وجود مسار غير مقيد `/api/auth/direct-access` يمنح وصول `Super_Admin` فوري دون أي كلمة مرور لأي مستخدم يقدم رمز الاستعادة المسرب.
   - تجاوز المصادقة في خادم Express (`server.ts:50`) لمنح حساب `awadh.a.1987@gmail.com` صلاحية Admin كاملة دون التحقق من أي كلمة مرور.
   - مسار `/api/companies` مكشوف للعامة بدون أي مصادقة، ويسرب جميع بيانات الشركات وتراخيصها وسجلاتها الضريبية والتجارية (`ResCompanyRead.license_key`).

3. **الامتثال للسوق السعودي وهيئة الزكاة والضريبة (ZATCA Compliance):**
   - محول ZATCA في `Backend/zatca_adapter.py` يمثل محاكاة محلية لترميز TLV وتجزئة SHA-256 وسلاسل الهاش (Chaining)، ولكنه **غير معتمد وغير متصل فعلياً** بمنصة "فاتورة" (Fatoora Portal) عبر شهادات التشفير الرقمي (CSID / ECDSA) ولا يملك إثبات اجتياز فحص الامتثال الرسمي من الهيئة.

4. **الحكم النهائي على الجاهزية:**
   - المنظومة **غير جاهزة إطلاقاً للبيع أو التشغيل الإنتاجي التجاري** بالحالة الراهنة. تحتاج إلى تنفيذ فوري لخطة المعالجة التنفيذية (Remediation Plan) بدءاً من إغلاق الثغرات الحرجة (P0) وتوحيد مصدر الحقيقة وعزل المستأجرين (P1).

### 3.3 إجابات قاطعة ومثبتة بالدليل على الأسئلة الإلزامية

1. **ما قاعدة البيانات التي يستخدمها Backend افتراضيًا فعلًا؟**
   - **الجواب:** يستخدم PostgreSQL 16 محلياً عبر الرابط: `postgresql+psycopg2://oxengl:oxengl@localhost:5432/oxengl`، كما هو معرف في `Backend/database.py:20-27`.
2. **ما قاعدة البيانات التي يستخدمها إعداد الإنتاج والـ Systemd؟**
   - **الجواب:** نفس قاعدة بيانات PostgreSQL 16 المحلية، حيث تشغل خدمة `oxengl.service` الملف `Backend.main:app` معتمدًا على المتغير `DATABASE_URL` في ملف `.env`.
3. **هل يستخدم Frontend قاعدة بيانات أو نظام تخزين مختلفًا؟**
   - **الجواب الصريح:** **نعم، وبشكل جذري.** واجهة React Frontend تستخدم المتصفح المحلي `localStorage` كمخزن أساسي للبيانات التشغيلية والمالية وسندات الصرف والكسارات، ولا تتصل بقاعدة بيانات PostgreSQL لمعظم العمليات اليومية.
4. **هل يتم تخزين البيانات في localStorage أو Firebase أو بيانات وهمية؟**
   - **الجواب:** نعم. يتم قراءة وحفظ كيانات الأعمال (`meayon_customers`, `meayon_crushers`, `meayon_transporters`, `meayon_operations`, `meayon_vouchers`) مباشرة في `localStorage` عبر `src/context/AppContext.tsx:532-568`. كما تسقط الواجهة على بيانات وهمية (`INITIAL_*`) عند أول تشغيل.
5. **ما مصدر الحقيقة لكل كيان تجاري؟**
   - **الشركات والمصادقة المؤسسية:** خادم FastAPI وقاعدة PostgreSQL (`res_companies`, `res_users`).
   - **العمليات والكسارات والناقلين وسندات الصرف في الواجهة:** المتصفح المحلي (`localStorage`) للمستخدم الحالي!
   - **فواتير المبيعات:** مشتتة بين `localStorage` وجدول `customer_invoices` في PostgreSQL بحسب الشاشة التي يتم إدخال الفاتورة منها.
6. **هل توجد مصادر حقيقة متعددة متنافسة؟**
   - **نعم.** هناك تنافس مباشر وفجوة خطيرة بين بيانات PostgreSQL المسجلة في `Backend` وبين مصفوفات الـ State المخزنة في `localStorage` داخل المتصفح.
7. **هل يمكن أن تفقد البيانات أو تختلف أو تصبح قديمة أو تظهر في متصفح واحد فقط؟**
   - **نعم، مؤكد 100%.** إذا فتح المدير المنصة من جهاز كمبيوتر محمول وأضاف عميلاً أو سجل تذكرة ميزان، فلن تظهر هذه البيانات للمحاسب الجالس على جهاز آخر، ولن تظهر في تقارير PostgreSQL الرسمية، وستختفي تماماً إذا قام المستخدم بمسح سجل المتصفح (Clear Cache/Storage).
8. **ما معمارية قاعدة البيانات المطلوبة لـ SaaS في الإنتاج، وما خطوات الترحيل إليها؟**
   - **المعمارية المطلوبة:** قاعدة بيانات PostgreSQL مركزية موحدة، تعتمد عزل المستأجر الصارم (Logical Tenant Isolation) عبر عمود `company_id` مفهرس ومحمي عبر سياسات Row-Level Security (RLS) أو طبقة وسطى ملزمة في الـ ORM، مع تحويل واجهة React لتكون بالكامل مبنية على استدعاءات REST API الموثقة، وتجريد المتصفح من دور تخزين البيانات التشغيلية.

## 4. تحليل Backend (FastAPI Architecture & Services)

### 4.1 المعمارية والتنظيم
- يتكون الـ Backend من ملف رئيسي عملاق `Backend/main.py` يحتوي على **4,109 أسطر كود**، يضم 162 مسار API، مع تداخل شديد بين منطق التوجيه (Routing)، ومنطق الأعمال (Business Logic)، واستعلامات قاعدة البيانات (Data Access).
- يرافقه ملف نماذج `Backend/models.py` (1,433 سطراً) يضم 37 نموذجاً، وملف مخططات `Backend/schemas.py` (2,353 سطراً).
- توجد بنية خدمات فرعية واعدة في مجلد `Backend/services/`:
  - `ai_governance.py`: محرك حوكمة الذكاء الاصطناعي مع قيود HMAC-SHA256 وتفويض بشري HITL.
  - `ai_parser.py`: محلل الفواتير الوثائقية واستخراج بنود الضريبة.
  - `ai_forecasting.py`: محاكاة تنبؤية للإنتاج الزراعي واستهلاك الوقود والمخزون.
- **العيوب المعمارية:** غياب طبقة Service Layer وRepository Pattern مستقلة في معظم المسارات التشغيلية اليومية داخل `main.py`، مما يجعل الملف متضخماً وصعب الصيانة والتعديل الآمن.

### 4.2 المصادقة وإدارة الجلسات
- يدعم النظام تشفير كلمات المرور باستخدام `passlib` مع خوارزميات `pbkdf2_sha256`, `argon2`, و`bcrypt`.
- آلية الجلسات تعتمد على ملفات تعريف ارتباط مشفرة أو موقعة (`session_token`) تحتوي على معرّف المستخدم ومعرّف الشركة ودوره (`sub`, `company_id`, `role`).
- **الثغرة الكبرى:** مسار `/api/auth/direct-access` ومسارات التخطي التي تتجاوز التحقق من كلمة المرور تماماً وتمنح جلسات `Super_Admin` و`Admin` فورية.

### 4.3 إدارة المستأجرين (Multi-Tenancy)
- يوفر الـ Backend معمارية متقدمة نظرياً لدعم نوعين من العزل:
  1. **العزل المنطقي (Logical Isolation):** معظم الجداول تمتلك مفتاحاً أجنبياً `company_id: UUID` مرتبطاً بجدول `res_companies.id`.
  2. **العزل الفيزيائي للشركات الكبرى (Physical DB Routing):** تم توفير `TenantConnectionManager` في `Backend/database.py:86` لتوجيه الشركات المشتركة في الباقة Enterprise إلى قواعد بيانات PostgreSQL منفصلة باستخدام نصوص اتصال مشفرة بـ AES-256 عبر Fernet.
- **نقاط الضعف المكتشفة:**
  - يتم استخراج المستأجر من الترويسة `X-Company-ID` مع التحقق من مطابقتها لبيانات المستخدم المسجل في الجلسة (`Backend/main.py:341`). هذا يمنع الـ IDOR البسيط للمستخدمين العاديين، ولكنه يسمح لحساب `Super_Admin` بتمرير أي `company_id` دون تدقيق صارم للتبديل بين السياقات.
  - بعض المسارات العامة (مثل `GET /api/companies`) لا تطبق فحص المستأجر وتسرب قائمة جميع المستأجرين وتفاصيل اشتراكاتهم.
